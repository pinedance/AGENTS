# My Code Review Executor

Interactively execute code review tasks generated by `my-code-review` (`tasks.md` / `task2.md`) while preserving codebase safety and preventing regression.

---

---

## Regression Prevention Protocol (실행 로직 부작용 방지 원칙)

리팩토링 및 코드 수정 과정에서 기존 실행 로직이 왜곡되거나 데이터 계산 결과가 변형되는 것을 차단하기 위해 다음 4대 방지 규칙을 엄격히 적용한다:

1. **Domain Calculation & Schema Invariance (도메인 연산 및 데이터 구조 불변성)**:
   * 수학 공식(G-Score, Dice 유사도 등), 통계 임계값, 행렬 계산식, 데이터베이스/JSON 출력 키 규약은 태스크 목표가 해당 수식의 버그 수정이 아닌 이상 **절대 임의 변형 금지**.
2. **Empirical Baseline Comparison (실행 기준값 사전/사후 비교 검증)**:
   * 🔴 **상** 또는 🟡 **중** 위험도 모듈 수정 전, 파이프라인/모듈 실행을 통해 **사전 기준 메트릭(레코드 수, 엣지 수, 출력 키)**을 기록.
   * 단순 구문 검사(`py_compile`)에 그치지 않고, 모듈 실행 검증을 통해 **사후 메트릭이 사전 기준값과 100% 일치하는지 비교 검증**.
3. **Explicit Side-Effect Impact Disclosure (부작용 영향 범위 구체적 고지)**:
   * `ask_question` 질의 시 "정상 데이터 경로(Happy Path) 영향 여부"와 "에러/경계 조건 경로(Error Path) 영향 여부"를 명확히 구별하여 고지.
4. **Surgical Diff Audit (수정 후 Git Diff 검수)**:
   * 파일 수정 직후 `git diff <file>`를 점검하여 지정된 태스크 영역 외에 인접 함수나 코드가 오염되지 않았는지 수술적 범위(Surgical Scope) 확인.

## Protocol & Execution Rules

### 1. Task File Discovery & Pre-flight
- Search for the latest code review session directory under `.agents/docs/my-code-review/<session_id>/`.
- Prioritize loading `task2.md` if available (ordered by Common Module -> Individual Files with Side-Effect Risk Ratings). Fall back to `tasks.md`.
- Parse remaining `TODO` tasks and identify current execution stage (`Stage 1: common.py`, `Stage 2: compile_json.py`, etc.).
- If no review task file is found, inform the user to run `my-code-review` first.

---

## 2. Interactive Task Execution Loop

For each remaining `TODO` task, strictly follow this 4-step loop:

### Step A: Output Detailed Task Summary & Side-Effect Explanation (As Visible Text)
- **Do NOT pack everything into the `ask_question` modal string.** First, write out a clear, detailed markdown response to the user containing:
  1. **Task Details & Location**:
     - Task ID, Title, Severity (🔴/🟡/🔵), and clickable File Link with line range (e.g. `[script/common.py:L38-L50](file:///absolute/path/to/script/common.py#L38-L50)`).
     - **What**: Concrete explanation of what code needs to be modified.
     - **Why**: Technical reason and coding guideline rule being violated.
  2. **Detailed Side-Effect & Risk Analysis**:
     - **Risk Rating**: 🔴 **상 (신중)** / 🟡 **중 (판단 필요)** / 🟢 **하 (바로 수정)**
     - **Concern & Risk Rationale (우려되는 부작용 원인 및 우려 이유)**:
       - **Mandatory for 🔴 상 & 🟡 중 Tasks**: Must explicitly explain **WHY** this modification is risky and **WHAT specific failure scenario is feared** if modified (e.g. *"Because changing `load_config()` return type from dict to dataclass will cause AttributeError in callers expecting bracket access `cfg['key']` if any call site is missed"*, or *"Because re-raising OSError in synonym generator might break deployment pipelines that rely on optional synonym file generation"*).
     - **Happy Path Impact**: State explicitly whether normal data calculations or output schemas are affected.
     - **Error Path Impact**: State how error handling, fail-fast behavior, or boundary conditions will shift.

### Step B: Call Focused `ask_question` Tool
- Immediately after outputting the detailed markdown explanation in Step A, call `ask_question` with a clean, focused question for execution approval:
  - **Question**: `[T-XX] <Title> (<File:Line>). 위 설명된 내용대로 수정을 진행할까요?`
  - **Options**:
    - `(Recommended) 예, 설명된 부작용/검증 방안 확인 후 적용 진행`
    - `이 태스크 건너뛰기 (Skip)`
    - `해당 파일 전체 맥락 먼저 확인`

### Step C: Execute, Compare & Verify
- **If User Chooses to Apply**:
  - Apply surgical edits using `replace_file_content` (adhering strictly to `my-coding-guidelines`).
  - Run verification command (syntax check `python3 -m py_compile <file>` AND empirical dry-run/module execution).
  - Compare post-execution output metrics against pre-execution baseline to confirm zero calculation regression.
  - Audit `git diff <file>` to ensure no adjacent logic was touched.
  - Update status in `task2.md` / `tasks.md`: `[x] DONE` and update counters (`Done: N+1 | Remaining: N-1`).
- **If User Chooses to Skip**:
  - Update status in `task2.md` / `tasks.md`: `[-] SKIPPED: <reason>` and update counters (`Skipped: N+1 | Remaining: N-1`).

### Step D: Proceed to Next Task
- Proceed automatically to the next `TODO` item in execution order until all tasks reach `DONE` or `SKIPPED`.

---

## 3. Post-Execution Verification & Summary
- Run full project verification / syntax compilation across all modified files.
- Execute full pipeline dry-run to verify overall data integrity.
- Present final execution summary table showing Total, Done, and Skipped tasks.
